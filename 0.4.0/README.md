# Лабораторна робота №4 — версія 0.4.0

## Опис

Розроблено односторінковий вебзастосунок (SPA) на основі архітектури клієнт-сервер із фронтенд-частиною, написаною на TypeScript, та серверною частиною на базі Express.js з использанням SQL.js.

## Архітектура системи

### Структура проекту
- **`index.html`** — точка входу клієнтської частини; завантажує зібраний `dist/app.js`.
- **`app.ts`** — основний модуль фронтенду; містить логіку управління формами, таблицями, фільтрацією та переглядом деталей.
- **`apiClient.ts`** — типізований HTTP-клієнт для взаємодії з серверним API; реалізує обробку таймаутів та нормалізовану обробку помилок у форматі ProblemDetails.
- **`shared/dtos.ts`** — спільний модуль типів даних, що використовується як фронтенд-частиною, так і серверною частиною для забезпечення типобезпеки контракту.
- **`backend/src`** — серверна частина на базі Express.js; містить маршрутизацію, сервіси бізнес-логіки, репозиторії для роботи з даними та централізовану обробку помилок.

## Запуск компонентів системи

### Встановлення та запуск клієнтської частини
1. Переміститись у директорію `0.4.0`:
   ```bash
   cd 0.4.0
   ```

2. Встановити залежності проекту:
   ```bash
   npm install
   ```

3. Зібрати фронтенд-частину:
   ```bash
   npm run build
   ```
   Скрипт компілює вихідні файли `app.ts` та `apiClient.ts` у виконуваний файл `dist/app.js` та `dist/apiClient.js`.

4. Запустити клієнтський застосунок через локальний веб-сервер або відкрити `index.html` безпосередньо у браузері.

### Встановлення та запуск серверної частини
1. Переміститись у директорію бекенду:
   ```bash
   cd 0.4.0/backend
   ```

2. Встановити залежності:
   ```bash
   npm install
   ```

3. Запустити сервер у режимі розробки:
   ```bash
   npm run dev
   ```

4. Альтернативно: зібрати та запустити у режимі продакшну:
   ```bash
   npm run build
   npm run start
   ```

Серверна частина доступна за адресою `http://localhost:3000`.

## Специфікація API

### Ендпоінти версії 1 (v1)
- `GET /api/v1/software` — отримання переліку записів про програмне забезпечення (підтримує query-параметри `license`, `page`, `pageSize`, `sortBy`, `sortOrder`)
- `GET /api/v1/software/{id}` — отримання інформації про конкретний запис за ідентифікатором
- `POST /api/v1/software` — створення нового запису про програмне забезпечення
- `PUT /api/v1/software/{id}` — оновлення існуючого запису
- `DELETE /api/v1/software/{id}` — видалення запису

### Ендпоінти версії 0 (без версійності)
- `GET /api/software` — отримання переліку ПЗ (еквівалент до `/api/v1/software`)
- `GET /api/users` — отримання переліку користувачів
- `GET /api/categories` — отримання переліку категорій

## Приклади запитів до API

### Отримання переліку програмного забезпечення
```bash
curl http://localhost:3000/api/v1/software
```

### Отримання запису за ідентифікатором
```bash
curl http://localhost:3000/api/v1/software/1
```

### Створення нового запису
```bash
curl -X POST http://localhost:3000/api/v1/software \
  -H "Content-Type: application/json" \
  -d '{"name":"VS Code","version":"1.90","license":"MIT","seats":10,"comment":"Editor","categoryId":"1"}'
```

### Оновлення запису
```bash
curl -X PUT http://localhost:3000/api/v1/software/1 \
  -H "Content-Type: application/json" \
  -d '{"version":"1.91","seats":15}'
```

### Видалення запису
```bash
curl -X DELETE http://localhost:3000/api/v1/software/1
```

### Обробка помилок (формат ProblemDetails)
При виникненні помилки сервер повертає відповідь у наступному форматі:
```json
{
  "status": 400,
  "title": "VALIDATION_ERROR",
  "detail": "Виявлено помилки при валідації вхідних даних",
  "errors": [
    { "field": "name", "message": "Поле є обов'язковим" }
  ]
}
```

## Основні характеристики реалізації

- **Версіонування API**: впровадження простої версійності API із префіксом `/api/v1/` для основних ендпоінтів; налаштування еквівалентних маршрутів для забезпечення зворотної сумісності.
- **Типизованість на TypeScript**: розроблення як клієнтської, так і серверної частини на мові TypeScript; централізоване сховище типів у модулі `shared/dtos.ts`.
- **Централізована обробка помилок**: імплементація middleware для уніфікації формату помилок; використання стандарту ProblemDetails для структурування відповідей.
- **Механізм таймаутів на клієнті**: впровадження AbortController для управління таймаутом запитів (12 секунд); коректна обробка сценаріїв скасування.
- **Налаштування CORS**: конфігурація CORS для конкретних джерел (origin) без використання підстановочного символу "*"; явне перелічення дозволених методів (GET, POST, PUT, DELETE) та заголовків.
- **Валідація даних DTO**: реалізація двоступеневої валідації — на сервері та на клієнті; виведення помилок валідації для кожного поля.
- **Функціональність клієнта**: фільтрування за типом ліцензії; пошук записів; можливість редагування, видалення та перегляду деталей.
- **HTTP-клієнт**: реалізація модуля `apiClient.ts` з функціями для типобезпечних запитів; автоматична обробка JSON-відповідей та генерування помилок типу `ApiClientError`.
- **Кешування на фронтенді**: список ПЗ кешується у пам'яті для повторного відкриття без зайвих запитів; кеш інвалідовується після створення, оновлення або видалення запису.
- **Retry тільки для безпечних запитів**: повторні спроби виконуються лише для `GET`/`HEAD` у випадку 429 або 503, з обмеженим числом спроб.

## Правила забезпечення сумісності контракту DTO

Для гарантування стабільності контракту між клієнтською та серверною частинами дотримуємось наступних принципів:

1. **Заборона видалення та перейменування існуючих полів**: якщо поле вже використовується клієнтською частиною (наприклад, `name`, `version`, `license`), його обов'язково мусить залишатися у серверній частині з тим же типом даних.

2. **Додавання нових полів як опціональних**: нові поля можуть впроваджуватись з дефолтними значеннями або як опціональні (з використанням типу `Partial`), щоб не порушувати сумісність зі старішими версіями клієнта.

3. **Консистентність структури відповідей**: список записів завжди повертається у форматі `{ data: T[], meta?: {...} }`, а окремий запис — у форматі `{ data: T }`. Зміна цієї структури забороняється.

## Примітки щодо експлуатації

- Для коректної роботи клієнтської частини файл `index.html` повинен завантажувати зібраний модуль `dist/app.js`.
- Перед запуском клієнтської частини переконатись, що серверна частина запущена та доступна за адресою `http://localhost:3000`.
- При старті серверної частини автоматично виконується скрипт `seed`, який заповнює базу даних тестовими даними.
- Усі текстові коментарі в вихідному коді написані мовою українська.
